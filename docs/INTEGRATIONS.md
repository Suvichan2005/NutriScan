# NutriScan integrations

All services are for local development. The application binds to `127.0.0.1:3400`. No provider key was installed, enabled or used during implementation. There is no deployment.

## Explicit remote actions

Local OCR, package editing, numerical analysis and browser storage do not use these routes. Clicking a disclosed public search sends its query to the named public service; product-candidate lookup may also send the selected country as a catalog-tag filter. Gemini routes require a separate consented action; images and profile context must not be sent automatically.

| Route | Strict request | Result |
| --- | --- | --- |
| `GET /api/status` | No body | `gemini.configured`, `enabled`, `model`, `searchEnabled`, explanation; no key or credential material |
| `POST /api/products` | `{query?:string,barcode?:string,alternatives?:boolean,country?:string,excludeBarcode?:string}`; country is optional for candidates and only applies a catalog-tag filter when supplied | `{status,products:ProductRecord[],message,requestId}` |
| `POST /api/research` | `{query:string,topic:'science'|'regulation'|'claims'|'brand'|'recalls'}` | `{status,items:ResearchItem[],message,requestId}` |
| `POST /api/assist` | `{consent:true,question,package,profile?,evidence?,calculations?,images?,conversationContext?}` | `{status,answer,claims,limitations,inspectImage,requestId}` |
| `POST /api/vision` | `{consent:true,image:{imageId,mimeType,base64,side,sourceImage:{width,height},preprocessing:{rotation,contrast,invert,crop}},instruction?}` | `{status,observations,visionCapture:{runId,imageId,side,sourceImage,processing,model},limitations,requestId}` |

Errors return `{status,code,message,requestId}` with a relevant HTTP status. `disabled` is separate from `unavailable`. An empty search is separate from a source failure. The UI must display these states honestly.

`images` in assist contains browser metadata only: `{handle,side,width,height}`. An optional `inspectImage:{handle,reason,crop?}` selects a known browser image. The crop uses normalized `x,y,width,height` within `[0,1]`. The browser owns that handle, previews/crops the original, and performs an explicit disclosed vision request. Unknown handles and out-of-bounds crops are rejected. No browser image is fetched by a server URL.

## Public services

Exact barcode lookups use the canonical Open Food Facts v2 product endpoint. Candidate name search uses the official Search-a-licious POST search service. The v2 product server does not support full-text search. Candidate requests return at most four matches and enrich each with at most one canonical product fetch. Alternative candidates can be searched globally or filtered by a country explicitly entered by the user; when a current package barcode is provided, that exact record is excluded from candidate results. Catalog country tags may be incomplete or stale and do not establish present availability. Candidate search does not rank healthfulness or imply a better formulation. All product records state `local stock unverified`.

Open Food Facts documents normalized nutrient fields with the `_100g` suffix as per 100 g, or per 100 ml for liquids ([nutrition schema](https://openfoodfacts.github.io/documentation/docs/Product-Opener/schemas/schemas/product_nutrition/); [export field definitions](https://github.com/openfoodfacts/openfoodfacts-server/blob/main/html/data-fields.txt)). NutriScan honors an explicit `100ml` basis. For a declared `100g` record whose package quantity unit is `ml`, it uses `100ml` only when the record's category tags identify a recognized beverage branch, and it warns that this volume basis is inferred from community data. A volume-packaged record outside those categories keeps its values with a `null` basis, so comparisons are withheld. `100g` records with no volume package unit retain a mass basis. Package quantity alone does not establish a basis. Sodium is converted from upstream grams to milligrams. Zero survives; missing, negative and non-finite values do not become zero. Crowdsourced records require comparison against the photographed regional package. Last-modified and retrieval timestamps are separate.

Science search uses Europe PMC core records. Free-text queries are Unicode-normalized into literal terms, common question/function words are dropped, and each remaining term must occur in the article title or abstract (`TITLE_ABS`); user-supplied search operators are not passed through. This improves topical scope but can reduce recall, especially for long or unusual phrasing. The route returns publication dates, publication type, abstract text when provided, canonical links, and DOI where valid. Results are discovery candidates. Relevance, human applicability, dose, study quality, retraction status, conflicts and consensus are not established. A protocol or review is not mislabeled as a completed randomized trial. The application does not infer causality from search matches. See the [Europe PMC REST API](https://europepmc.org/RestfulWebService) and [search syntax guide](https://europepmc.org/searchsyntax).

Regulation/claim discovery uses a fixed registry of primary FSSAI and WHO pages. A retrieved page excerpt is plain text, never rendered HTML. FSSAI discovery cannot establish consolidated current law, an effective date, authorization or package compliance. No arbitrary external URL fetch is offered.

The registry also includes the official 24 March 2026 Labelling and Display Gazette PDF, with separate publication and stated effective dates. The server accepts PDFs only from the existing HTTPS host allowlist, requires `application/pdf` plus the `%PDF-` signature, caps the download at 1.2 MB, and extracts at most 40 pages / 50,000 characters with PDF.js. Scanned pages are not OCRed, excerpts are not interpreted, and later rules/orders still require review. In a direct local probe on 21 October 2026, the official PDF URL responded HTTP 200 with `text/html`; the research path rejected it. A later Windows `curl.exe -I` probe on the same day rejected TLS for the official page and PDF with Schannel `CRYPT_E_REVOKED`. The UI now retains official source-link cards when retrieval fails, clearly labeled as navigation only; it does not present a synthetic excerpt. The fixture tests prove PDF parsing, bounds and date separation, not live FSSAI availability.

`brand` and `recalls` search the fixed public openFDA food-enforcement endpoint without an API key. At most four records, sorted by report date, are returned as **historical United States candidate matches**. Each retains exact recall number, firm, product description, lot/code, distribution, report and initiation dates when provided, source link and dataset-update caveat. This is not a universal brand-credibility score, an Indian recall check, a live alert or a recall-lifecycle service. FDA warns that recorded status may not be updated after classification. Empty results do not establish safety or absence of recalls; failures are reported separately. No consumer reviews are scraped or invented.

## Gemini activation and boundaries

The pinned `@google/genai` SDK (`2.30.0`) uses `models.generateContent` with `responseMimeType:'application/json'` and `responseJsonSchema`, followed by independent Zod and evidence validation. The SDK's `models.list()` returns a `Pager`; project-specific availability is checked against its `page` and `supportedActions`, rather than inferred from the public catalogue. Current SDK references: [Models.list and generateContent](https://googleapis.github.io/js-genai/release_docs/classes/models.Models.html), [Model.supportedActions](https://googleapis.github.io/js-genai/release_docs/interfaces/types.Model.html), and [GenerateContentConfig](https://googleapis.github.io/js-genai/release_docs/interfaces/types.GenerateContentConfig.html). Provider calls use a low thinking level and explicit output bound with no automatic continuation. Free-tier application requests allow at most one retry for HTTP 503, after a short jittered exponential backoff; paid application requests and synthetic smoke checks remain single-attempt. This avoids hiding duplicate paid attempts inside the one-call spend ledger while handling Google's documented temporary-capacity error. Built-in search remains disabled even if its environment flag is set. See Google's [troubleshooting guidance](https://ai.google.dev/gemini-api/docs/troubleshooting).

Assist claims cite existing package-observation IDs, supplied source IDs, deterministic calculations, or nonempty user-context fields. Unknown and empty citations fail validation; unknown image handles fail validation. Each cited item needs an exact supporting span in the server-held text. Claims may be direct quotations or concise synthesis: the server discards the model's free-form answer, rebuilds bounded output from validated claims, labels paraphrases as interpretations, and includes fixed safety copy. Exact spans establish traceability, not entailment, source authenticity or answer completeness; obvious medical/safety wording is filtered as defense in depth, not as a complete safety validator. Tentative structured candidates must cite original OCR lines and remain separate from package facts. When a cited OCR line includes word metadata, a candidate must also point to one or more role-tagged word indexes on each such line; the server checks those references against the preserved line text and token list. Candidate interpretations now render separately from the answer and are not passed through the OCR parser or used in calculations. The consented text request includes raw OCR observations, their capture/provenance metadata and parser diagnostics, plus supplied retrieval sources and calculations. If the user also opts into photos, the client selects up to three relevant session photos, locally resizes each to at most 900 KB, and sends them with the OCR and question in the same structured assist request; no image is uploaded by default. A separate user-triggered image-inspection action remains for a specific crop when useful. The client clears `package.rawText` only when every non-empty line exactly matches the ordered raw OCR observations (ignoring the merge-generated photo separator), since the observation list is the richer duplicate-free record; mixed or unmatched text is retained. Text-only assist requests remain capped at 300 KB. Photo-enabled assist accepts at most three compressed images, has a 4.3 MB total HTTP-body limit, and a 2.7 MB combined sanitized-image limit; oversize requests fail without partial truncation. Package image provenance is session-scoped through image handles and capture IDs, not a durable image digest. Structured output syntax is type-checked locally; live structured model output remains unverified: the owner-authorized two-photo package request reached the paid route but Google returned HTTP 429, so no generated output was validated.

Before a consented assist request is built, the browser combines sources already visible in the investigation: the deterministic audit's references, local semantic-search candidates and results of any source search the user ran. The adapter deduplicates IDs, bounds the context to 15 sources and summaries to 1,600 characters, records unspecified jurisdiction as unknown, and preserves each research result's search classification in its summary. Non-HTTPS and local URLs are omitted here and rejected again by the server. The provider instructions treat research results as discovery candidates and require their limitations to remain in view. Recent conversation turns are excluded unless separately opted in; their answers can establish follow-up intent but never evidence. The normal text route includes image handles only.

Vision accepts JPEG, PNG and WebP, canonical base64, maximum 2 MB encoded source bytes and 24 megapixels. MIME signatures and actual decoding are both checked. The server strips metadata and produces a bounded JPEG before transmission. Every returned observation is linked to the selected session image and a unique vision run; `visionCapture` records side, source dimensions, normalized crop, rotation, contrast/invert settings and model identifier. The client-supplied source dimensions describe the original photo while the submitted bytes may already be a prepared crop; the server cannot verify those dimensions or crop against original bytes. Package validation requires each linked vision observation to resolve to its matching capture. A later assist request preserves this lineage and checks any matching live image handle. No original bytes or durable image digest are stored by this lineage record. Vision observations remain unverified; confidence is model-reported and uncalibrated. An owner-authorized two-photo package request was assembled and sent after the disclosed Analyze action, but Google returned HTTP 429; no Gemini answer or real-photo interpretation quality has been accepted.

## Request bounds and privacy

Every POST requires local hostname, exact same-origin browser Origin and JSON content type. Host must be a loopback authority on the existing local request port. The validated Host handles Next's localhost normalization when the actual browser visits 127.0.0.1; forwarded hosts are ignored. Cross-site requests are rejected before work. Product/research routes allow 8/10 requests per minute respectively; assist and vision share 4 requests per minute. Each group permits at most two active requests. The assist route accepts at most 300 KB for text-only requests. When the user separately opts into images, it accepts at most 4.3 MB total JSON for bounded OCR line/word evidence and up to three compressed photos, with a 2.7 MB combined sanitized-image limit; excess requests are rejected, never partially forwarded. These in-memory limits are appropriate to the single local development process, not a distributed production limiter.

Public fetches have fixed HTTPS destination hosts, no credentials, no ports, redirect rejection, a 12-second deadline, content-type checks and byte caps. Request JSON is streamed with byte limits. Gemini uses a 25-second client deadline, no automatic retries/continuation, 4,000 output tokens, a 160 KB provider-response ceiling and a 50 KB structured-text ceiling. Provider input is capped at 300 KB for text-only requests and 4.5 MB when inline images are present. Neither request bodies nor images, profile context, conversations, keys or raw provider failures are logged by these modules.
