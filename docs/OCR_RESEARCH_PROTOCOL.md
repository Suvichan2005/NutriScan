# NutriScan package-photo OCR research protocol

Updated 21 October 2026. This is a public, product-neutral experiment protocol; it contains no university-specific formatting or institutional claims. The live application remains a mobile-first web/PWA product. Browser-first OCR is the current baseline. No production engine change or Gemini activation is authorized by this research track.

## Research question and comparison boundary

Measure how reliably OCR systems turn real package photographs into grounded nutrient observations. Compare browser Tesseract.js, local/server OCR (currently RapidOCR with PP-OCRv6 small), the official PaddleOCR.js PP-OCRv5 browser SDK, and—only after separate owner authorization—Gemini direct vision and adaptive hybrid OCR. All candidates must receive the same original image bytes, human annotations, canonical output schema, parser/scoring rules, and split. A candidate may have a separately reported production-preparation path, but results must identify that preprocessing and may not be called input-identical.

The independent evaluation unit is a product, not a photo or nutrient row. Keep every image, language variant, package revision, and crop from the same GTIN/product family in one split. Use exploration/tuning products only for development. Lock held-out product IDs and annotation before running a candidate; no tuning or threshold changes after opening the held-out results. If a held-out set has not been provisioned, report `not run`, never an exploratory score as held-out or population accuracy.

## Current data and provenance

The five-photo comparison in `data/semantic-photo-manifest.json` is a convenience sample of public Open Food Facts package photos, all previously exposed to OCR exploration. It contains 37 manually transcribed nutrient fields, images from multiple languages and markets, and no independent product- or photo-level held-out evaluation set. It is useful for debugging and comparing current candidates, not for estimating population accuracy. The photographs are hash-checked at run time; local image bytes remain in the ignored `docs/evidence/private/` directory and are not committed.

The manifest links each photo to its Open Food Facts product page, source image URL, uploader, SHA-256, dimensions, visible basis, and human-read package values. Open Food Facts documents its product image terms as CC BY-SA and its database as ODbL; each experiment release must retain attribution to the uploader/source and applicable ShareAlike/ODbL terms. The image terms do not settle third-party packaging, logo, or trademark rights. Verify the source license and terms again before redistribution. Do not bundle source photographs in the public repository. A future public dataset release should publish a provenance/annotation manifest and retrieval instructions, subject to license review, while keeping any non-redistributable images in a controlled local evaluation store.

Human annotations are visual transcriptions, not laboratory assays, regulatory verification, or proof that a separately sourced product has the same formulation. Preserve printed decimal precision, explicit unit, column/basis, language, and ambiguity. Do not annotate missing values as zero. Add image-level annotations for visible table bounds, row bands, column/basis headers, and legibility before the locked evaluation run; retain adjudication notes and annotator agreement. When annotation is uncertain, mark it uncertain and exclude it from exact-value scoring while reporting the excluded count.

## Canonical extraction and scoring contract

Every engine adapter must emit the same logical result: image identity/hash; engine, model/version and configuration; crop/preprocessing; detected text-line geometry and confidence; extracted nutrient key, numeric value, unit, serving basis and source line/region; abstention or error reason; and timing/resource/network observations. Preserve raw OCR only in the local process needed for extraction and scoring. Persist sanitized per-image/per-field outcomes, not image bytes or raw OCR strings, in tracked receipts. The shared contract must preserve conflicting candidates and distinguish missing from zero.

The proposed output contract is `data/ocr-evaluation-receipt.schema.json`. Dataset records and region/row/column annotation shape are defined by `data/ocr-dataset.schema.json`; neither schema includes image bytes. The currently available five-photo manifest is not yet compliant with the region-annotation schema and remains a development set. Do not silently upgrade it to held-out data.

Score each annotated field as one of `exact`, `incorrect`, `omitted`, `abstained`, `unscorable`. An exact numeric match requires canonical key, numeric value within a predeclared tolerance, unit, and serving basis all correct. Report numeric-only, unit, and basis correctness separately so a value copied from the wrong column cannot pass as a correct field. Explicit model abstention is different from silence/omission. An incorrect emitted value counts as a false positive and a false negative for exact field detection. Report precision, recall, exact-field accuracy, coverage, omissions, abstentions, and incorrect readings with denominators and product-level breakdowns. Never collapse omitted and abstained or exclude wrong values from error rates.

Separate pipeline stages using the image annotations and line geometry: (1) text-region detection recall/precision against annotated text/table regions; (2) character/word or field-label recognition; (3) numeric recognition; (4) row/column association and nutrition-table reconstruction; (5) unit and serving-basis association; (6) parser acceptance/rejection and the final grounded observation. A box near an annotated row is detection evidence only; it does not prove text recognition. Without annotated regions or token transcriptions, report that stage as unavailable rather than infer it from final parser output. Publish per-image/per-field sanitized stage flags so failures can be traced without storing source text.

## Operational measures

Record cold initialization and warm per-image latency separately, plus repeated-run median and p95 when enough repetitions exist. Measure peak process RSS for local/server paths; browser JavaScript heap, WebAssembly linear memory where available, and browser process RSS separately. Record compressed model/runtime transfer bytes, cache state, model artifact size, and any image bytes sent to a remote service. Document hardware, OS, browser/runtime, CPU/GPU, thread count, network profile, power/thermal state, input pixel dimensions and preprocessing. Do not compare browser heap with full process RSS as if they were equivalent.

For Gemini or another remote service, report the selected model and dated published pricing assumptions, token/image accounting assumptions, retries, average and p95 requests per audit, projected cost per image and per 1,000 audits, plus privacy/data-transfer behavior. Do not call the provider or claim a measured provider cost before explicit owner authorization. For private/local models, report artifact size, runtime/license, expected hosting hardware and a transparent cost estimate with assumptions rather than inventing a price.

## Reproducibility and release gate

Commit the manifest schema, annotation guide, locked split IDs/hashes, adapter versions, commands, sanitized receipts and a concise analysis. Keep tuning records distinct from final locked-set results. Any preprocessing, threshold, parser or model selection after seeing held-out results creates a new development experiment and requires a new untouched held-out set. Keep browser journey acceptance, local synthetic tests, public provider calls, photo accuracy, and held-out accuracy in separate evidence categories.

An OCR replacement is eligible for product consideration only after a sufficiently diverse, independently annotated, product-held-out comparison shows a repeatable gain in exact grounded fields without unacceptable wrong readings, latency, device memory, download, privacy or operating cost. One small sample or a better test count is insufficient. Research readiness is not production integration or acceptance.

## Current status

`docs/evidence/ocr-paddleocr-v5-browser.json` and `docs/evidence/rapidocr-evaluation.json` are exploratory comparative receipts, not held-out research results. On their shared five-image/37-field full-frame sample, browser-prepared Tesseract scored 2 exact / 0 incorrect, RapidOCR 7 / 0, and PaddleOCR.js PP-OCRv5 6 / 0. The one-field RapidOCR/Paddle difference is not meaningful evidence of superiority at this sample size. The Paddle harness used an approximate vertical-row grouper; it loaded external model assets but kept image bytes in local Chrome memory. No baseline currently provides fully annotated detection/recognition/column ground truth, so those stage scores remain incomplete. Gemini remains disabled. The current product reader remains unchanged.
