# NutriScan package-photo OCR research protocol

Updated 21 October 2026. This is a public, product-neutral experiment protocol; it contains no university-specific formatting or institutional claims. The live application remains a mobile-first web/PWA product. Browser-first OCR is the current baseline. No production engine change or Gemini activation is authorized by this research track. Shared Zod contracts cover dataset schema v2, independent annotation pass schema v1, transient extraction schema v1, and sanitized per-image receipt schema v2.

## Research question and comparison boundary

Measure how reliably OCR systems turn real package photographs into grounded nutrient observations. Compare browser Tesseract.js, local/server OCR (currently RapidOCR with PP-OCRv6 small), the official PaddleOCR.js PP-OCRv5 browser SDK, and—only after separate owner authorization—Gemini direct vision and adaptive hybrid OCR. All candidates must receive the same original image bytes, human annotations, canonical output schema, parser/scoring rules, and split. A candidate may have a separately reported production-preparation path, but results must identify that preprocessing and may not be called input-identical.

The independent evaluation unit is a product, not a photo or nutrient row. Keep every image, language variant, package revision, and crop from the same GTIN/product family in one split. Use exploration/tuning products only for development. Lock held-out product IDs and annotation before running a candidate; no tuning or threshold changes after opening the held-out results. If a held-out set has not been provisioned, report `not run`, never an exploratory score as held-out or population accuracy.

## Current data and provenance

The five-photo comparison in `data/semantic-photo-manifest.json` is a convenience sample of public Open Food Facts package photos, all previously exposed to OCR exploration. It contains 37 manually transcribed nutrient fields, images from multiple languages and markets, and no independent product- or photo-level held-out evaluation set. It is useful for debugging and comparing current candidates, not for estimating population accuracy. The photographs are hash-checked at run time; local image bytes remain in the ignored `docs/evidence/private/` directory and are not committed.

The manifest links each photo to its Open Food Facts product page, source image URL, uploader, SHA-256, dimensions, visible basis, and human-read package values. Open Food Facts' [official license guidance](https://openfoodfacts.github.io/documentation/docs/Product-Opener/api/tutorials/license-be-on-the-legal-side/) distinguishes the database (ODbL), individual contents (DbCL), and product photographs (CC BY-SA); the [official API documentation](https://openfoodfacts.github.io/openfoodfacts-server/api/) repeats those terms. Each experiment release must retain uploader/source attribution and applicable ShareAlike/ODbL obligations. The image terms do not settle third-party packaging, logo, or trademark rights. Verify source license and terms again before redistribution. Do not bundle source photographs in the public repository. A future public dataset release should publish a provenance/annotation manifest and retrieval instructions, subject to license review, while keeping any non-redistributable images in a controlled local evaluation store.

For candidate tooling, record code, model, converted-weight, runtime, and dictionary/license provenance separately, including model artifact URL/hash/license in the engine receipt. The [official PaddleOCR.js guide](https://github.com/PaddlePaddle/PaddleOCR/blob/main/paddleocr-js/packages/core/README.md) documents browser inference and returns line polygons, recognized text, confidence, detection/recognition timings, and runtime metadata. It is an OCR line pipeline; nutrition-column interpretation remains a separate layer. PaddleOCR's [repository license](https://github.com/PaddlePaddle/PaddleOCR/blob/main/LICENSE) covers the project, while each model artifact must also be identified. RapidOCR's [official repository](https://github.com/RapidAI/RapidOCR) describes its Apache-2.0 implementation and Paddle-derived weights; retain the exact model source and hash with each receipt. SDK license alone is not a substitute for model-artifact provenance.

The current locked development dependency is `@paddleocr/paddleocr-js@0.4.2`. The official SDK documents browser execution of PP-OCRv5, line polygons/text/confidence, detection and recognition timings, runtime metadata, and optional worker mode. Model and WASM downloads remain network-transfer measurements even when the image itself stays in the browser. Re-check official API and asset behavior against the exact package and model hashes used for each run; do not assume the repository's moving `main` branch describes a prior benchmark release.

Human annotations are visual transcriptions, not laboratory assays, regulatory verification, or proof that a separately sourced product has the same formulation. Preserve the exact printed number text, its numeric interpretation and qualifier, explicit unit, column/basis, language, geometry, and ambiguity. Do not annotate missing values as zero. The local `/research/ocr-annotation` workflow accepts a local image, hashes it in the browser, captures normalized table/row/label/value/unit/basis rectangles and exports one strict, single-reader pass. It has no OCR, provider call, remote upload, persistent draft, image bytes, local path, or file name in the export. The public candidate registry supplies attribution fields only; excluded low-legibility images are not selectable. This is annotation tooling, not an accuracy measurement.

For each reference image, two readers independently annotate from the same original pixels before seeing OCR output or each other's pass. Use anonymous reader codes. Annotate every visible nutrient row from top to bottom, including ambiguous rows; record table, row, label, value, unit, basis, and column regions where visible. Do not infer unreadable values from product databases, nutrient arithmetic, serving calculators or other product variants. After both passes are exported, compare each field dimension separately, adjudicate disagreements against the source pixels, and preserve unresolved values as ambiguous or not visible. Keep the independent passes and adjudicated reference version distinct. Human-verified is allowed only after two readers, adjudication, agreement methodology and required field geometry are recorded. Report inter-reader agreement for label/key, literal numeric transcription, numeric value/operator, unit, basis kind/amount/unit, column association and region alignment; state the formula and denominator for every aggregate.

`npm run ocr:compare-annotations -- <reader-a.json> <reader-b.json>` validates distinct reader codes and exact image identity, compares rows by top-to-bottom array order, reports per-dimension agreement with denominators, and summarizes normalized bounding-box IoU by region role. It is a comparison aid, not an adjudicator: field-order mismatches, unpaired rows, region pairings, ambiguity and all printed-value disagreements require human review before producing a merged reference record.

## Canonical extraction and scoring contract

Every engine adapter must emit the same logical result: image identity/hash; engine, model/version and configuration; crop/preprocessing; detected text-line geometry and confidence; extracted nutrient key, numeric value, unit, serving basis and source line/region; abstention or error reason; and timing/resource/network observations. Preserve raw OCR only in the local process needed for extraction and scoring. Persist sanitized per-image/per-field outcomes, not image bytes or raw OCR strings, in tracked receipts. The shared contract must preserve conflicting candidates and distinguish missing from zero.

The common interfaces are `data/ocr-annotation-pass.schema.json`, `data/ocr-dataset.schema.json`, `data/ocr-extraction.schema.json` and `data/ocr-evaluation-receipt.schema.json`, generated from strict Zod definitions in `src/lib/contracts.ts`. Reference fields retain `printedNumericText` beside normalized `numericValue`/operator, unit and basis. `src/lib/ocr-evaluation.ts` validates image identity and scores one image without collapsing conflicting candidates. The extraction interface may carry OCR text only transiently for local scoring; tracked receipts keep normalized nutrient candidates and stage outcomes but omit source text and image bytes. Receipts retain their reference status so single-reader or model-assisted annotations cannot be presented as human-verified.

The currently available five-photo manifest is not yet compliant with the region-annotation schema and remains a development set. `data/ocr-photo-candidate-register.json` records three new, hash-checked Open Food Facts source photos awaiting independent human annotation and one low-legibility photo excluded from a clear numeric reference. The source images remain ignored under `docs/evidence/private/`; no OCR engine has run against these candidates. Do not silently upgrade either set to a human-verified held-out evaluation set.

Score each annotated field as `exact`, `incorrect`, `omitted`, `abstained` or `unscorable`; unmatched extra candidates are separate false positives. Exact requires canonical key, exact numeric value/operator, unit and serving basis. Keep literal printed numeric text as a reference audit field; the exact-value outcome is based on the separately transcribed numeric interpretation and qualifier. The pilot tolerance is zero because values are transcribed at printed precision; any nonzero tolerance must be declared before the run. Exact-field precision is exact fields divided by all scorable emitted candidates; predictions matched to unscorable references are counted separately and excluded from this denominator. Exact-field recall is exact fields divided by clear, scorable annotations. Coverage is clear expected fields with a candidate for the canonical key divided by clear, scorable annotations, even when the candidate's value, unit or basis is wrong. Numeric, unit and basis accuracy each use the full clear expected-field denominator, so omissions do not disappear from component accuracy. Report numeric, unit, basis and end-to-end precision/recall with raw numerators, denominators and product-level breakdowns. Explicit model abstention is different from silence/omission. Preserve every conflicting candidate. Never exclude wrong readings from error rates.

Separate pipeline stages using the image annotations and line geometry: (1) text-region detection; (2) field-label and numeric recognition; (3) row/column association and nutrition-table reconstruction; (4) unit recognition; (5) serving-basis recognition; (6) parser acceptance/rejection and the final grounded observation. The current pilot detection rule matches a detected text polygon when it covers at least 50% of a reference polygon's bounding-box area. A box near a row is detection evidence only; it does not prove recognition. Stage scores are conditional on having the required annotation and candidate geometry. Without annotated regions or token evidence, report that stage as unavailable rather than infer it from final parser output. The receipt keeps normalized stage flags and a bounded parser-rejection code, never recognized source text.

## Operational measures

Emit one receipt conforming to `data/ocr-evaluation-receipt.schema.json` per image, retaining per-field outcomes and stage flags. Keep run identity and product-group split stable across engine receipts so records can be joined by image hash and field ID. Record cold initialization and warm per-image latency separately, plus repeated-run median and p95 when enough repetitions exist; one-run results must leave those summaries unavailable. Mark memory as a peak or sample and identify its scope: process RSS for local/server paths; browser JavaScript heap, WebAssembly linear memory where available, and browser process RSS separately. `networkBytes` counts all transferred bytes during the run; `imageTransferBytes` counts image payload bytes sent to a service, not local worker copies; `modelBytes` counts unique model artifacts transferred. Record cache state, model artifact size, and all image bytes sent remotely. Document hardware, OS, browser/runtime, CPU/GPU, thread count, network profile, power/thermal state, input pixel dimensions and preprocessing. Do not compare browser heap with full process RSS as if they were equivalent. Report model download separately from per-image inference transfer, and label metrics unavailable when the runtime cannot measure them; do not fill resource fields with estimates. Cost estimates must include source URL, date, currency, request/image assumptions and deployment assumptions. A cost is measured only if actually billed or metered.

For Gemini or another remote service, report the selected model and dated published pricing assumptions, token/image accounting assumptions, retries, average and p95 requests per audit, projected cost per image and per 1,000 audits, plus privacy/data-transfer behavior. Do not call the provider or claim a measured provider cost before explicit owner authorization. For private/local models, report artifact size, runtime/license, expected hosting hardware and a transparent cost estimate with assumptions rather than inventing a price.

## Reproducibility and release gate

Commit the manifest schema, annotation guide, locked split IDs/hashes, adapter versions, commands, sanitized receipts and a concise analysis. Keep tuning records distinct from final locked-set results. Any preprocessing, threshold, parser or model selection after seeing held-out results creates a new development experiment and requires a new untouched held-out set. Keep browser journey acceptance, local synthetic tests, public provider calls, photo accuracy, and held-out accuracy in separate evidence categories.

An OCR replacement is eligible for product consideration only after a sufficiently diverse, independently annotated, product-held-out comparison shows a repeatable gain in exact grounded fields without unacceptable wrong readings, latency, device memory, download, privacy or operating cost. One small sample or a better test count is insufficient. Research readiness is not production integration or acceptance.

## Current status

`docs/evidence/ocr-paddleocr-v5-browser.json` and `docs/evidence/rapidocr-evaluation.json` are exploratory comparative receipts, not held-out research results. On their shared five-image/37-field full-frame sample, browser-prepared Tesseract scored 2 exact / 0 incorrect, RapidOCR 7 / 0, and PaddleOCR.js PP-OCRv5 6 / 0. The one-field RapidOCR/Paddle difference is not meaningful evidence of superiority at this sample size. Paddle's approximate row reconstruction showed label and expected-number token presence more often than parser output, but same-row and token-presence checks are proxies: they do not isolate detection or recognition accuracy. In particular, true table-column association cannot be separated from parser rejection or basis/unit parsing without independently annotated text regions, row/column geometry, and transcripts. Treat association, basis/unit and parser acceptance as candidate bottlenecks to test, not as causal findings from the current sample. The Paddle harness loaded external model assets but kept image bytes in local Chrome memory. Gemini remains disabled. The current product reader remains unchanged. The common evaluator has passed unit checks for zero versus missing, basis mismatch, omission versus explicit abstention, conflicting candidates, privacy-safe receipts and image-hash mismatch; it has not yet produced a new OCR accuracy result. The local annotation route now exports single-reader passes, but no new candidate photo has been double-annotated, adjudicated, or promoted to held-out status. Three source photos remain pending independent human review; the low-resolution Weet-Bix label is excluded from clear numeric scoring.
